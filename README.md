# Детекция ботов-сборщиков данных по событиям в суточном окне

Для каждой `cookie_id` из `test.csv` модель выдаёт `score` ∈ [0, 1]: насколько вероятно, что это трафик
сервиса автоматизированного сбора данных. Метрика — Precision при Recall ≥ 0.7 (официальный `metric.py`).

## Результат

| Модель | P@R70 (OOF, временная CV) | PR-AUC | ROC-AUC |
|---|---|---|---|
| Baseline из quickstart: RandomForest на `n_events`, `item_nunique` | 0.093 | 0.202 | 0.609 |
| LightGBM, 111 поведенческих признаков | 0.787 | 0.792 | 0.941 |
| LightGBM, + 13 признаков разобранного UA | 0.790 | 0.796 | 0.942 |
| Ансамбль, только поведенческие признаки | 0.797 | 0.796 | 0.942 |
| **Финал: ансамбль LightGBM + CatBoost + ExtraTrees, поведение + разобранный UA** | **0.822** (CI90 0.756–0.857) | **0.800** | **0.943** |

Доля ботов 8.1%, случайный скор даёт ~0.08. Полная история экспериментов с цифрами — [`EXPERIMENTS.md`](EXPERIMENTS.md).

## Запуск

Python 3.13.10, точные версии библиотек зафиксированы в `requirements.txt`. Все зависимости open-source и работают
локально: pandas, numpy, scikit-learn, LightGBM, CatBoost. Внешних API и предобученных моделей нет.

```bash
pip install -r requirements.txt
python3 train.py        # ~7 мин на MacBook Air: все эксперименты + submission.csv
python3 train.py --only blend_final --no-ablation   # только финальная модель и сабмит, ~1–2 мин
python3 validate.py     # необязательно: adversarial validation, кластеры ботов + LOCO, тюнинг
```

Ожидаемая структура: `data/{train.csv, test.csv, events.csv.gz}` и `metric.py` рядом со скриптами.
Все источники случайности зафиксированы (`SEED = 42`, сиды моделей 42…46). Многопоточность тоже не влияет на результат:
LightGBM с `deterministic=True`, фиксированное число потоков CatBoost, предсказание ExtraTrees в один поток —
повторный запуск даёт побайтно тот же `submission.csv`.

| Файл | Назначение |
|---|---|
| `features.py` | загрузка, очистка событий, окно, все признаки |
| `train.py` | временная CV, baseline vs финальная модель, контрольные эксперименты, ablation, `submission.csv` |
| `validate.py` | проверки устойчивости (на сабмит не влияет) |

| `results/` | `experiments.csv`, `feature_importance.csv`, `univariate_auc.csv`, `oof_final.csv` и др. |

## Признаки

Все считаются только по событиям внутри окна куки, то есть доступны на момент `window_end_ts`.
Префикс имени = группа (используется в ablation). Вклад — изменение P@R70 LightGBM (0.790 на финальных признаках) при удалении группы.

| Группа | Что описывает | Почему (EDA) | Вклад |
|---|---|---|---|
| `p_` курсор | доля web/desktop-событий без координат; шаг между соседними точками, автокорреляция x/y, центр и размах, доля точек на границе экрана | люди кликают равномерно по экрану 1920×1080 (std x ≈ 1920/√12), независимые точки, медианный шаг 745 px; боты — блуждание (шаг ~280 px), упоры в границы, у 67% их web-событий курсора нет вовсе | **−0.17** (0.790 → 0.619), самая важная |
| `t_` тайминг | квантили интервалов внутри сессии, доли ≤ 2/5/10/30 с, CV, std лог-интервалов | медиана Δt: боты 14 с, люди 46 с; различие сильнее в хвостах (q75, q90); на мобильных — главный сигнал | −0.02 P@R, −0.017 PR-AUC; без группы 4-й фолд падает до 0.69 |
| `c_` контент | число и энтропия категорий, городов, объявлений; повторные просмотры; фото на просмотр | сборщик обходит много городов и категорий, человек ищет в своём | **−0.04** (PR-AUC −0.023) |
| `u_` разобранный UA | тип клиента (приложение Avito / браузер), ОС, версия и её отставание, число платформ и UA на куку, противоречие UA ↔ platform | среди мобильных ботов 67% ходят через UA приложения `okhttp` (люди — 38%): сбор через API приложения | в LightGBM ≈0, в ансамбле +0.026 (0.797 → 0.822) |
| `s_` поиск | глубина пагинации, линейность обхода 1→2→3, страниц на запрос | max page: боты 7, люди 4 (90-й перцентиль 20 vs 9) | нейтрально |
| `v_` объём | события, сессии (разрыв > 30 мин), пиковая активность в минуту | | нейтрально |
| `e_` действия | доли типов событий, частые биграммы переходов, контакт прямо из выдачи | боты реже листают фото, добавляют в избранное, логинятся | нейтрально |
| `h_` время суток | доли ночи/утра/дня/вечера, энтропия по часам | боты активнее ночью | нейтрально |
| `a_` куки | возраст куки на начало окна, создана ли в окне, доля дублей | медиана возраста: боты 19 дней, люди 62 | нейтрально |

Нейтральные группы оставлены: удалять признаки по разнице, лежащей внутри шума CV, — значит подгонять под шум.

**Про User-Agent.** Сырая строка UA и её частота (`u_ua_popularity`) в модель не идут: это идентификатор конкретного
сервиса, а не описание поведения, и на нём модель выучила бы «список ботов». Разобранные поля описывают *тип клиента*
и *противоречия в трафике* (несколько платформ при одном UA, UA не сходится с платформой). Проверка на переобучение
под сервисы — LOCO ниже: с разобранным UA и без него перенос на незнакомый тип ботов одинаковый.

## Модель

Ранговое среднее трёх моделей на одних и тех же 124 признаках: LightGBM (400 деревьев, 5 сидов), CatBoost
(600 итераций, 5 сидов), ExtraTrees (500 деревьев). Ранги, а не вероятности — метрике важен только порядок,
а шкалы вероятностей у моделей разные. Метрика отмечает равные `score` группой, поэтому ничьи в сумме рангов
разбиваются средней вероятностью трёх моделей (осмысленный вторичный скор, а не случайный шум).

На тех же 124 признаках: LightGBM 0.790, CatBoost 0.817, ансамбль **0.822** (PR-AUC 0.796 / 0.798 / 0.800).
Выигрыш ансамбля над CatBoost в пределах шума; ансамбль оставлен как более диверсифицированный вариант — три
разных по устройству модели меньше зависят от случайностей одной из них. Гиперпараметры не тюнились сверх базовых: 9 конфигураций LightGBM дали
разброс внутри доверительного интервала.

## Валидация

* **Временная**: test (20–26.04) лежит сразу после train (6–19.04). Скользящая схема из 4 фолдов: валидация на
  2 днях (12–13, 14–15, 16–17, 18–19.04), обучение на всех днях раньше.
* **Главная цифра — P@R70 по склеенным out-of-fold предсказаниям** всех фолдов (~475 ботов). В одном фолде
  ~120 ботов, метрика там шумит на ±0.03–0.05; для финала считается 90% бутстреп-интервал.
* **Без early stopping**: число деревьев фиксировано. Остановка по валидационному фолду подглядывала бы в ту же
  выборку, на которой считается оценка.
* Различия меньше ~0.02 не считались значимыми; решение принималось, только если P@R70 и PR-AUC сдвигаются в одну сторону.

## Утечка и сдвиг: что нашли и как закрыли

1. **Утечка из будущего.** Первая версия считала популярность объявления (сколько других кук его смотрели) по всем
   дням train+test: для куки от 6 апреля признак видел просмотры 26 апреля. Эксперимент
   `lgb_with_itempop_leaky` показывает цену ошибки: **0.891** против 0.790 у той же модели без него — +0.10 фиктивного качества.
2. **Сдвиг, внесённый своим же признаком.** Честная накопительная версия («все просмотры до конца окна куки»)
   растёт от начала train к test: у поздних кук больше истории. Adversarial validation (модель отличает train от
   test) давала **ROC-AUC 0.886**, 68% сигнала — этот признак. Версия с окном 1 сутки убрала сдвиг
   (**AUC 0.516**), но перестала давать прирост → группа исключена.

## Устойчивость к новым сервисам (`validate.py`)

Боты train кластеризуются по поведению (KMeans на квантильно нормализованных признаках без UA, k по silhouette):

| | люди | «быстрый обходчик» | «медленный» |
|---|---|---|---|
| кук | 10 192 | 483 | 416 |
| медиана Δt, с | 48 | 15 | 45 |
| событий | 12 | 35 | 10 |
| глубина выдачи | 4 | 11 | 4 |
| городов | 5 | 12 | 5 |
| возраст куки, дней | 62 | 6 | 27 |
| доля web-событий без курсора | 0.07 | 1.00 | 1.00 |

**Leave-one-cluster-out** (ROC-AUC на людях + ботах кластера, тип был в обучении / исключён из обучения):

| | без UA | с разобранным UA |
|---|---|---|
| «быстрый обходчик» | 0.969 / 0.830 | 0.970 / 0.830 |
| «медленный» | 0.908 / 0.669 | 0.908 / 0.671 |

Модель уверенно ловит **известные** источники, но на незнакомый сервис — особенно «медленный», с человеческим
темпом — переносится плохо. Это главное ограничение решения. Для этой постановки (test из тех же источников)
оно приемлемо. Структура кластеров слабая (silhouette 0.2): это приближение к «сервисам», а не их восстановление.

## Разбор ошибок

При пороге, дающем recall 70% на OOF: recall ботов на web 0.81, на android 0.51, на iOS 0.36 — на мобильных нет
курсора. Куки с 1–3 событиями не ловятся (их 11 ботов из 475). Пропущенные боты — «медленные» со старыми куками;
ложные срабатывания — «быстрые люди» без курсора. Это и определяет потолок: сигнал для мобильных и коротких кук
почти исчерпан признаками тайминга.

## Ограничения и как это жило бы в продакшене

* Модель учит почерк известных сервисов; новый сервис требует дообучения (LOCO). В проде — мониторинг доли
  срабатываний и дрейфа признаков, регулярное переобучение на свежей разметке.
* Главный сигнал — курсор. Сервис, эмулирующий равномерные клики, его обойдёт; тогда нагрузка ляжет на тайминг
  и паттерн обхода. На мобильных курсора нет изначально — там качество заметно ниже.
* Оценка на CV шумная (CI90 шириной ~0.12): решения принимались по согласованному сдвигу нескольких метрик.
* Порог здесь выбирает проверяющая система; в проде его выбирали бы под пропускную способность модерации и
  стоимость ложной блокировки человека.
